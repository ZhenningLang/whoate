whoate · 架构投影

本文只用一个抽象层级：进程与数据源层。框是一个独立运行的进程、一个 Rust 库里的大块职责，或者 whoate 读取的一个外部数据源；不画函数和文件。

1. 一句话它是什么

whoate 是一个 Rust 写的归因引擎库，被两个出口共用：给人看的菜单栏应用，和给助手、脚本调用的命令行。引擎读系统接口、tmux 和各家助手的会话记录，把「进程」翻译成「归属 + 证据 + 诊断」。

核心概念

  • 归属：它是什么——一个人认得出的资源主人（tmux pane、助手会话、应用、孤儿、系统服务）。守着什么规则——每个进程恰好记在一个归属下，归属内存之和等于全机总和。谁围着它转——归因步骤写它；诊断、命令行输出、界面列表都读它。
  • 归因证据：它是什么——把进程记到某个归属的一条理由，带来源与可信度。守着什么规则——没有证据的归属不允许出现，证据按可信度从高到低排。谁围着它转——采集提供原料，归因步骤生成，界面详情和 whoate why 原样展示。
  • 诊断：它是什么——对一个归属的一句话判断，分 ok / watch / act 三档。守着什么规则——每个归属恰好一个诊断，只有 act 档带建议动作。谁围着它转——规则表生成，菜单栏排序、命令行退出码、关闭按钮都依赖它。

这张图想让读者看懂：三个核心概念都在引擎里，命令行和菜单栏只是同一份结果的两个出口，外部数据源全部只读。

3. 新增 / 复用 / 退役

全部是新建，没有退役。新增依赖与 overview.md 登记的同一批：clap（U-DEP-1）、serde（U-DEP-2）、libc（U-DEP-3）、rusqlite（U-DEP-4）、CI 测试机（U-DEP-5）、安装公式仓库（U-DEP-6）。复用系统框架 SwiftUI、Swift Charts、MenuBarExtra 与系统自带 top、tmux。

whoate/
├── crates/whoate-core     引擎：采集、归因证据、归属、诊断
├── crates/whoate-cli      出口一：命令行
├── crates/whoate-ffi      引擎的 C 接口，给菜单栏应用链接
└── app/                   出口二：SwiftUI 菜单栏应用

4. 容量与上界

  • 进程数：本机 904 个，按 5000 个设计上限；快采一遍 702 个用 4ms，线性外推 5000 个约 30ms [推断：线性外推，没在 5000 进程的机器上测]。
  • 系统进程补齐：top 一次 2.5 到 3.6 秒，后台每 6 秒一次，数据最多旧 6 秒（命令行最多 30 秒）。
  • 曲线内存：每个归属 1800 个点 × 16 字节 ≈ 28KB，200 个归属约 5.6MB。
  • 命令行：有缓存 300ms 内、无缓存 500ms 内返回。
  • 菜单栏应用自身：目标 1 秒刷新平均 CPU 低于 1%，未验证（U-SPK-6）。

5. 关键决策与被否方案

决定一：引擎用 Rust，界面用 SwiftUI，两边用 C 接口传 JSON 字符串。改这条会炸哪：命令行与界面的数据从同一份 JSON 来，换成逐字段的 C 结构体后两边就会各自漂移。

决定二：归因按固定顺序取第一条成立的证据。改这条会炸哪：「每个进程只记一次」的规则；如果改成打分合并，同一进程可能被两个归属各算一半。

决定三：给助手的 JSON 只加字段不改字段（U-GATE-2）。改这条会炸哪：所有已写进助手说明和脚本的字段名。

Drawbacks

C 接口传 JSON 每秒多一次序列化与解析，量级在毫秒内 [推断：按 200 个归属、每个约 1KB 估算]。SwiftUI 方案让界面代码全部是 Swift，Rust 贡献者改不了界面。

Alternatives

Tauri（Rust 后端加网页界面）：最容易做漂亮，但多占约百兆内存，owner 否决。uniffi 生成 Swift 绑定：类型安全，但要多一套代码生成工具链，且 SwiftPM 无 Xcode 构建未验证；不做的后果是手写六个 C 函数，可接受。菜单栏应用直接每秒调用命令行子进程：最简单，但每秒起一个进程，自身 CPU 会超预算。

Unresolved questions

本轮定：五件待决策见 approval.md 第 2 节。实现时定：top -n 0 是否仍输出全部进程行（P1 spike）；曲线采样是否在 GUI 隐藏时降到 5 秒。out-of-scope：Linux 移植、MCP 薄壳。

6. 失败怎么被人发现

  • 慢采失败：JSON 顶层 system_procs 变成 stale 或 missing，界面状态栏显示「系统进程 N 秒前」并变黄。
  • 会话记录解析失败：对应证据标 weak，界面显示「数据稍旧」；命令行加 --debug 时把原因打到 stderr。
  • 引擎崩溃：菜单栏图标变灰并显示「采集失败」，日志写 ~/Library/Logs/whoate/whoate.log（按 5MB 轮转保留 3 份）。

7. 还没验证的假设

  • 每秒刷新时界面自身 CPU 低于 1%（U-SPK-6）[未验证：要等 P4 有界面才能测]。
  • top -n 0 仍输出全部进程行 [未验证：P1 第一步测]。
  • 5000 个进程时快采仍在 50ms 内 [推断：线性外推]。

8. 代号与术语表

  • U-GATE: 不可逆动作（单向门）
  • U-DEP: 新增依赖
  • U-SPK: 翻车假设与 spike
  • U-BEH: 有意行为变化
  • 快采：用 macOS 进程接口读本账号进程，毫秒级。
  • 慢采：用系统自带 top 补齐其他账号进程，秒级，后台跑。
  • footprint：macOS 统计的进程内存，含被压缩和换出的部分，与活动监视器「内存」列一致。
  • whoate/v1：命令行 --json 与界面共用的数据格式版本号。
